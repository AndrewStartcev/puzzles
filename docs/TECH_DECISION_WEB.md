# Мир пазлов — техническое решение

**Статус:** зафиксировано 2026-09-12  
**Решение:** production-версию игры делаем как браузерное приложение, не на Godot.

## Название

Рабочее название продукта: **«Мир пазлов»**.

Название «Уютные пазлы» больше не используется как основное: продукт должен свободно включать природу, животных, города, архитектуру, космос, машины, фэнтези, искусство, еду, путешествия и другие коллекции.

## Production-стек

- **Vite** — сборка и dev-server;
- **React** — интерфейс приложения;
- **TypeScript** — игровая и продуктовая логика;
- **PixiJS / WebGL** — игровое поле пазла;
- **SCSS/CSS** — интерфейс, адаптив и визуальные состояния;
- браузерное хранилище + платформенное облачное сохранение через адаптеры.

Next.js для этой игры не нужен: проект является SPA/HTML5-игрой и не требует SSR.

## Почему не Godot в production

Godot-прототип доказал главный технический принцип: одна исходная картинка может автоматически превращаться в пазл без ручной нарезки деталей.

Однако продукт вырос до большого puzzle-hub:

- 35+ коллекций;
- сотни изображений;
- каталоги, фильтры, длинные списки и модальные окна;
- магазин, daily, задания, профиль и настройки;
- режимы от простых пазлов до ~3000 деталей;
- большое поле с zoom/pan;
- виртуализированный лоток деталей;
- сохранение тысяч позиций;
- разные SDK Яндекс Игр и Пикабу.

Для такой структуры web-stack проще поддерживать, быстрее верстать и легче оптимизировать под браузер.

## Принцип данных пазла

Исходное изображение хранится один раз.

```text
assets/puzzles/nature/mountains.webp
```

Метаданные описывают контент отдельно:

```json
{
  "id": "nature_mountains_01",
  "title": "Горное озеро",
  "collection": "nature",
  "tags": ["горы", "озеро", "природа"]
}
```

Сами детали создаются процедурно во время запуска пазла.

## Работа с 1000–3000 деталями

Ключевое правило: большое количество деталей не должно означать микроскопическое игровое поле.

- рабочая поверхность увеличивается;
- камера имеет zoom/pan;
- игровой renderer работает через PixiJS/WebGL;
- данные деталей хранятся как лёгкие структуры, а не как тысячи DOM-компонентов;
- tray виртуализируется и рисует только видимую часть;
- геометрия восстанавливается по seed;
- сохраняются позиции/статусы деталей и состояние камеры, а не тяжёлые графические объекты.

Пример структуры детали:

```ts
interface PuzzlePieceState {
  id: number;
  row: number;
  col: number;
  x: number;
  y: number;
  targetX: number;
  targetY: number;
  placed: boolean;
}
```

## PlatformAdapter

Внутренняя игровая логика не должна зависеть от конкретной площадки.

```text
PlatformAdapter
├── LocalAdapter
├── YandexAdapter
└── PikabuAdapter
```

Через адаптеры подключаются:

- сохранения;
- реклама;
- профиль;
- платежи;
- лидерборды/достижения, если они понадобятся.

## Статус Godot-прототипа

Текущий Godot-код **не удалять**.

Он остаётся техническим прототипом и референсом для:

- процедурной геометрии деталей;
- совместимых соседних стыков;
- snap-механики;
- экспериментов с формой пазла;
- проверки математических идей.

Production-реализацию переносим в TypeScript/PixiJS.
